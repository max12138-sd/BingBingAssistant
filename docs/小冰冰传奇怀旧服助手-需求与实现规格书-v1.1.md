## 1. 产品定义

### 1.1 一句话

一个**常驻悬浮球**：点一下就能（1）看你正在打的那个阵容，给出更强的配法；（2）看未来 7 天有什么活动。

### 1.2 解决什么问题

| 痛点 | 方案 |
| --- | --- |
| 竞技场/巅峰配阵容靠试错 | 读屏识别双方阵容 → 本地模拟 → 给 Top 方案 + 胜率区间 |
| 巅峰高分段对方阵容被隐藏，凭感觉配 | 不完全信息下的**鲁棒决策**，给"稳健/均衡/搏杀"三套方案 |
| 未来活动埋在二级入口，过期才发现 | 读日历页 → 7 天视图 + 临期通知 |
| 推荐出来的阵容自己没这些英雄 | 「我的英雄库」作为硬约束 |

### 1.3 明确不做

变速 / 自动战斗 / 代点 / 修改数据 / 抓包 / root / 容器 / iOS / 鸿蒙 NEXT 原生。

## 5. 核心算法规格

> 本节是项目的大脑。**严格按伪代码实现**，变量名保持一致。

### 5.1 单场战斗模拟 `BattleSimulator`

简化模型，目标不是还原战斗，而是**相对排序正确**。

```kotlin
/**
 * @return true = A 胜
 * @param nSim 模拟次数，内部对 nSim 次求多数（或外部循环）
 */
fun simulateOnce(a: List<Combatant>, b: List<Combatant>, rng: Random): Boolean {
    // Combatant: heroId, atk, hp(cur), maxHp, def, spd, skills, pos, isHealer
    // 1) 复制双方状态
    // 2) 每回合：按 spd 降序（同速随机）依次行动
    // 3) 行动规则：
    //    - HEAL 型：给己方血量比例最低者回复 hp = atk * coef
    //    - AOE 型：对敌方全体造成 atk * coef * mitigation
    //    - CONTROL 型：使目标跳过下次行动（概率 0.35）
    //    - 其余：攻击敌方"最前排存活者"
    //    mitigation = 1 - def / (def + 600f)   // 600 为调参常数
    //    crit = if (rng.nextFloat() < 0.15f) 1.5f else 1f
    //    counter = if (attacker.counterTags contains target.tag) 1.15f else 1f
    // 4) 最多 30 回合；超时按 (剩余总 hp / 初始总 hp) 比值判胜负
    // 5) 返回 a 是否获胜
}

/** 返回 A 对 B 的胜率（0.0..1.0） */
fun winRate(a: List<MyHero>, b: List<MyHero>, nSim: Int = 300): Float
```

> 参数（600 / 0.15 / 1.5 / 1.15 / 30）全部放 `SimConfig` 单例，便于后续校准，不要散落。

### 5.2 胜率矩阵与对位求解 `WinMatrix`

**核心思想**：先算「我方第 i 队 vs 对方第 j 队」的成对胜率，得到 N×N 矩阵；再在对位全排列里找最优。这样模拟次数是 N² 而不是 N!。

```kotlin
/** N = 3（巅峰三队）或 5（传奇以上五队） */
fun buildMatrix(myTeams: List<List<MyHero>>,
                oppTeams: List<List<MyHero>>,
                nSim: Int): Array<Array<Float>>   // [i][j] = 我 i 胜率

/** 枚举全排列（N=3 → 6 种；N=5 → 120 种），返回期望胜场最大的对位 */
fun bestMatching(matrix: Array<Array<Float>>): Pair<IntArray, Float>
// 返回：perm[k] = 我方第 k 队应对对方第 perm[k] 队；以及期望胜场
```

### 5.3 分队候选生成 `CandidateGenerator`

#### 5.3.1 三队（15 英雄，从我的英雄库里取）

组合数 `C(15,5)×C(10,5)/3! ≈ 1.26×10⁵`，**可全枚举**，但麒麟 980 上仍建议粗排。

```kotlin
fun generate3(myPool: List<MyHero>, topN: Int = 200): List<TeamPlan> {
    // 1) 全枚举三种分队（去重，忽略队伍顺序）
    // 2) 对每个方案用解析式快速打分：
    //    score = Σ_team ( teamAtk*0.4 + teamHp/100*0.35 + teamDef*0.15 + synergyBonus*0.1 )
    //    synergyBonus：同阵营 ≥3 人 +5，纯输出无前排 -10
    // 3) 按 score 降序取 topN
}
```

#### 5.3.2 五队（25 英雄，传奇段位以上）

组合数约 `5×10¹²`，**绝不可枚举**，必须启发式。

```kotlin
fun generate5(myPool: List<MyHero>, topN: Int = 80): List<TeamPlan> {
    // 1) 初始解（贪心分层）：
    //    按综合战力降序排列 25 人，用"蛇形分配"填入 5 队：
    //    第1轮 0,1,2,3,4 → 队0..4；第2轮 9,8,7,6,5 → 队0..4（反向）；依此类推
    //    目的：让 5 队强度尽量均衡（因为要 3 胜，均衡比堆强更重要）
    // 2) 局部搜索：重复 3000 次
    //    - 随机选两队，各随机选 1 人交换
    //    - 用解析式 score 评估；若变好则接受
    //    - 模拟退火：以 exp(Δ/T) 概率接受变差解，T 从 1.0 线性降到 0.01
    // 3) 收集搜索过程中出现过的较优解，按 score 取 topN（去重）
}
```

### 5.4 鲁棒评估 `RobustEvaluator`

#### 5.4.1 隐藏位采样 `OpponentSampler`

**关键约束（C1）**：每队固定隐藏 3 个，但**隐藏位置不固定**（可能藏 1/2/3 位，也可能藏 2/4/5 位）。因此采样时必须尊重**已知槽位索引**——已看到的那 2 个位置是确定的，只对另外 3 个位置采样。

```kotlin
/**
 * @param oppPartial 对方各队：5 个 Slot，其中 2 个 VISIBLE（含 index 与 heroId），3 个 HIDDEN
 * @param bracket    "LEGEND" 等，用于取热度先验
 * @param m          采样套数（默认 40）
 */
fun sample(oppPartial: List<Team>, bracket: String, m: Int): List<List<List<MyHero>>> {
    // 对每队、每个 HIDDEN 槽位：
    //   1) 候选池 = 该段位热度 topK（K=30）的英雄，排除已在本队出现的
    //   2) 按 weight 做加权无放回抽样
    //   3) 星级：按该段位常见星级分布抽样（默认 5 星，概率 0.7；4 星 0.3）
    // 同一次采样内，全局 25/15 个英雄不可重复
}
```

#### 5.4.2 评估

```kotlin
fun evaluate(plans: List<TeamPlan>,
             oppSamples: List<OpponentWorld>,   // 每套 = 完整对方 N 队
             needWins: Int,                     // 3队=2，5队=3
             nSimPerPair: Int = 120): List<ScoredPlan> {
    // 对每个候选方案 × 每套对手世界：
    //   1) buildMatrix（N² 次 winRate）
    //   2) bestMatching → 该世界的胜场数（把胜率>0.5 记为 1 胜；
    //      更严谨可对每场按胜率做一次伯努利抽样）
    // 汇总出胜场分布 dist: Map<Int,Int>
    // 计算：
    //   p10Wins        = 分布的 10% 分位
    //   expectedWins   = Σ k*p(k)
    //   probAtLeastNeed= Σ_{k>=needWins} p(k)
    //   probPerfect    = p(N)
}
```

#### 5.4.3 三套方案

```kotlin
fun pickThreePlan(scored: List<ScoredPlan>): List<Plan> = listOf(
    scored.maxBy { it.probAtLeastNeed }!!.copy(style = "SAFE"),      // 稳健
    scored.maxBy { it.expectedWins }!!.copy(style = "BALANCED"),    // 均衡
    scored.maxBy { it.probPerfect }!!.copy(style = "AGGRESSIVE")    // 搏杀
)
// 若三者重叠，用"次优且不同"的方案替换，保证三套阵容确实不同
```

**为什么不能纯 OCR**：日历是月视图网格，活动起止日藏在「色块覆盖哪些格子」里。

```kotlin
fun parse(bitmap: Bitmap): List<ParsedActivity> {
    // 1) 灰度 → 二值化（Otsu） → 形态学开运算去噪
    // 2) 霍夫直线 / 投影法 检出横竖网格线 → 得到 rows × 7 的格子坐标
    // 3) 定位当月 1 号：
    //    - OCR 识别顶部"YYYY年MM月" → 得到年月
    //    - 计算 1 号是星期几 → 与第一行第一个非空格子对齐
    // 4) 建立 cell(r,c) → date 映射
    // 5) 在每个 cell 内做主色统计（HSV 众数），聚类得到 k 种"活动色"
    // 6) 对每种颜色，取被覆盖的 cell 集合 → 最小/最大日期 = 起止日
    // 7) OCR 识别底部图例区文字 → 颜色 ↔ 活动名 对应
    // 8) 跨月处理：若色块延伸到上月尾/下月头，标记 endDateConfidence = 0.5
    // 9) 与 DB 缓存交叉校验：名称匹配上的，用缓存补齐起止日
}
```

> 输出 `dateConfidence`：网格线全检出 + 图例 OCR 成功 = 0.9；缺图例 = 0.6；跨月 = 0.5。
> UI 上 `dateConfidence < 0.7` 的活动必须显示「日期待确认」。

## 6. 视觉识别规格

### 6.1 总体策略

**能不用 OCR 就不用。** 英雄头像用模板匹配（头像是固定贴图，比 OCR 准且快）；OCR 只读两类：英雄名（作互校）、活动名与日期。

### 6.2 处理流水线

```
截图(Bitmap) → 缩放到 720p 宽 → 按屏幕宽高比加载 LayoutProfile
  → ScreenClassifier 判定界面类型
  → [阵容类] SlotDetector 找 5 个卡槽 → HeroMatcher 逐槽匹 → OCR 辅助校验
  → [日历类] CalendarGridParser
```

### 6.3 布局配置外置（多设备关键）

**禁止硬编码坐标。** 所有坐标用**归一化值（0..1）**存在 assets 里，按「宽高比 + 界面类型」索引：

```json
// assets/layouts/peak5_2340x1080.json
{
  "screenAspect": 2.1667,
  "peaks": {
    "myTeams": [
      { "slot0": [0.08,0.30,0.07,0.16], "slot1": [0.16,0.30,0.07,0.16], ... }
    ],
    "oppTeams": [ ... ]
  }
}
```

运行时：`DeviceProfile.pick(aspect)` 选最接近的配置；无匹配则按最近比例缩放。

### 6.4 卡槽存在性检测 `SlotDetector`（C1 带来的关键改动）

因为**隐藏位置不固定**，不能假设"第 1、2、3 位可见"。必须逐槽判断：

```kotlin
fun detect(region: Bitmap): List<SlotState> {
    // 对预设的 5 个槽位区域分别判断：
    //   - 若该区域主色接近"暗底 + 问号/剪影色" → HIDDEN
    //   - 若检测到头像轮廓（边缘密度 > 阈值）→ VISIBLE
    //   - 若区域为纯背景 → EMPTY
    // 注意：HIDDEN 与 EMPTY 要区分开，前者代表"有英雄但被隐藏"
}
```

### 6.5 头像匹配 `HeroMatcher`

```kotlin
fun match(cardBitmap: Bitmap): MatchResult {
    // 1) 裁出卡面区域，转灰度 + 直方图均衡
    // 2) 对手/我方 5 张模板中做多尺度匹配（0.85 / 1.0 / 1.15）
    // 3) 取最大 TM_CCOEFF_NORMED
    // 4) score >= 0.82 → 直接判定
    //    0.70..0.82 → 用 OCR 读名字做二次确认
    //    < 0.70 → UNKNOWN（铁律 L4：不许猜）
}
```

### 6.6 OCR 引擎 `OcrEngine`

- 模型：RapidOCR PP-OCRv4 mobile（det / rec / cls），放 `assets/models/ocr/`，首启解压到 `filesDir/models`。
- 只对**小 ROI** 调用（单次裁图 ≤ 200×80），**禁止全图 OCR**。
- 单次超时 800ms，超时返回 null 走降级。

## 10. 非功能与性能预算（麒麟 980 为准）

| 项 | 目标 | 说明 |
| --- | --- | --- |
| 常驻内存 | ≤ 60 MB | Bitmap 用完必须 recycle |
| 待机 CPU | ≤ 2% | 无识别时不跑 OpenCV |
| 冷启动到浮球 | ≤ 2.5s | Application 里异步加载 OCR 模型 |
| 竞技场识别 | ≤ 3s | — |
| 巅峰 3 队 | ≤ 6s | 含算法 |
| 巅峰 5 队 | ≤ 10s | 含算法 |
| APK 体积 | ≤ 60 MB | 模型约 15MB，头像约 1MB |
| 离线 | 100% | 无网络权限 |

### 10.1 性能关键点

1. 截图后**先缩放再处理**，全程不在原尺寸上跑 OpenCV。
2. 所有识别走 `Dispatchers.Default`，主线程只做 UI。
3. 模板匹配按槽位并行（5 个协程）。
4. Bitmap 池化复用，避免频繁 GC（8GB 机器 GC 抖动会掉帧）。

## 15. 术语

| 术语 | 含义 |
| --- | --- |
| 可见槽 / 隐藏槽 | 巅峰中对方每队 5 个位置，2 个可见、3 个隐藏，**位置随机** |
| 信息完整度 | 可见英雄数 / 总数，3 队 = 6/15，5 队 = 10/25 |
| 胜率矩阵 | N×N 矩阵，`[i][j]` = 我方 i 队胜对方 j 队的概率 |
| 对位求解 | 在 N! 种匹配中找期望胜场最大者（3队6种，5队120种） |
| 悲观值 / P10 | 胜场分布的最差 10% 分位 |
| 达标条件 | 3 队制 ≥2 胜，5 队制 ≥3 胜 |
| 鲁棒优化 | 求"最坏情况也不太差"的方案，而非"平均最好" |
| 模板匹配 | 用小图在大图中定位的 CV 方法（TM_CCOEFF_NORMED） |
| ROI | 只处理关心的屏幕小区域，省算力 |

## 附录 B · 怎么查手机 SDK_INT（C2 的答案）

```kotlin
Log.i("DEVICE", "SDK_INT=${Build.VERSION.SDK_INT}, " +
    "${Build.MANUFACTURER} ${Build.MODEL}, ${Build.DISPLAY}")
```

也可以看：**设置 → 关于手机 → 版本号**（HarmonyOS 4.0.0.121 对应的是 AOSP 内核版本，实际 API 级别以上面日志为准）。
